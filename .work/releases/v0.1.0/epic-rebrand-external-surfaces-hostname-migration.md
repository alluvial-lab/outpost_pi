# Migrate production hostnames to kevoun.com

## Brief

Mechanical replacement of the remaining `jacobmoura.work` production
hostnames across product source, migrating to `kevoun.com` subdomains. No UX
change, no wire change — these are display/config constants and doc
references. `kevoun.com` is already the org domain for schema `$id` URIs
(the wire-stable migration moved `remote-pi.dev` → `kevoun.com`); this
extends that to the runtime hostnames.

The site is not live, so these are constant updates, not DNS cuts — the
code carries the new target even if the host doesn't resolve yet.

## Epic context

- Parent epic: `epic-rebrand-external-surfaces`
- Position in epic: independent mechanical feature; runs in parallel with F1
  (no-default relay) and F3 (rp-s3 retirement). Owns the
  `outpost-pi.jacobmoura.work` and legacy `remote-pi.jacobmoura.work`
  hostnames only — `relay-rp1` retires in F1, `rp-s3` retires in F3.

## Foundation references

- `docs/VISION.md` keeps the self-hosted, non-SaaS posture; this does not add
  a hosted service or alter the relay trust model.
- `docs/SPEC.md` / `docs/ARCHITECTURE.md` keep generated wire contracts and
  runtime transport separate from presentation/download URLs. No protocol
  schema, generated client, or relay URL is changed here.

## Design decisions

- **Homepage/download target:** `outpost-pi.kevoun.com` — it is the reasonable
  subdomain default while the operator's DNS decision remains pending, keeps
  the product's site identity separate from the apex, and is consistent with
  the epic's `rp-s3` → `dl.kevoun.com` naming direction. It is deliberately a
  literal-only implementation choice: change this one approved hostname map
  before implementation if the operator instead selects `kevoun.com`.
- **Legacy homepage mapping:** `remote-pi.jacobmoura.work` →
  `outpost-pi.kevoun.com` — old brand URLs must not survive in user-facing
  assets; they do not merit a redirect/compatibility layer in code.
- **Historical changelog:** leave `CHANGELOG.md` unchanged — it has no owned
  homepage hostname today, and its `relay-rp1` historical record belongs to
  the sibling relay-retirement transition.
- **Installer ownership:** `pi-extension/install.sh` is canonical;
  `site/public/install.sh` is a tracked synchronized copy regenerated by
  `site/scripts/sync-install-sh.mjs` during `pnpm build`. Edit the canonical
  script, then verify the generated tracked copy instead of maintaining two
  independent sources.
- **Out-of-scope hostnames:** do not change `relay-rp1.jacobmoura.work` or
  `rp-s3.jacobmoura.work`. In particular, preserve the `rp-s3` manifest URL
  in `site/src/lib/{cockpit-release,app-release}.ts`; F3 owns it. In
  `cockpit-release.ts`, this feature owns only the six mock artifact URLs
  currently using the homepage host.
- **Branding asset:** absorb `rebrand-branding-assets-redraw` as a manual SVG
  story. The banner needs text and layout review; it is not eligible for a
  blind string replacement.

## Architectural choice

Three approaches were considered:

1. **Scoped literal migration (chosen).** Replace only the two owned hostname
   families in their actual user-facing constants, docs, scripts, metadata,
   and test assertion. This has the smallest blast radius and preserves the
   adjacent relay/distribution decisions owned by F1/F3.
2. **Create a cross-project homepage URL registry.** This would centralize a
   value but cannot serve package metadata, shell scripts, Markdown, SVG, and
   two Dart/Next runtimes without generated artifacts or build coupling. It
   adds machinery for a one-time bounded migration.
3. **Wait for DNS and retain the old literals.** This leaves public install,
   support, metadata, and mock-download links on an unrelated hostname. DNS is
   expressly non-blocking, so this fails the epic's external-identity goal.

The selected approach changes only static values; it introduces no port,
adapter, wire shape, type, API signature, or lifecycle ownership concern.

| `outpost-pi.jacobmoura.work` | `outpost-pi.kevoun.com` | Mechanically replace in URLs, metadata, scripts, docs, release-mock artifact URLs, and update fallbacks. |

## Implementation Order

1. `story-epic-rebrand-external-surfaces-hostname-migration-mechanical-replacement`
   — baseline-worker-eligible bounded replacement, generated-installer sync,
   and all automated/static verification.
2. `story-epic-rebrand-external-surfaces-hostname-migration-branding-svg-redraw`
   — depends on story 1; manual asset edit and visual validation close the
   final legacy homepage reference.

The dependency intentionally serializes the final old-host scan after all
mechanical replacements. It also keeps the layout-sensitive SVG outside a
mechanical worker's bulk-replacement scope. The implementation tier is
**baseline**: story 1 is suitable for one bounded baseline worker; story 2
requires manual SVG editing/review even when delegated. `work-view --blocking`
was checked before adding the dependency and found no cycle.

## Risks

- **DNS is not yet live / final hostname is operator-adjustable.** The code
  will intentionally carry a potentially non-resolving target. Before an
  implementation starts, a final operator choice can replace the one mapping
  table value; do not retain old hosts while waiting for DNS.
- **F2/F3 share `site/src/lib/cockpit-release.ts`.** A broad replacement could
  migrate F3's `rp-s3` manifest URL. The story narrows the owned edit to six
  mock artifact URLs and requires a focused diff review.
- **SVG typography may overflow.** The fallback is a manual coordinate/font
  adjustment followed by a rendered 1280×640 review, never a blind `sed`.
- **Tracked installer duplication can drift.** The fallback is to rerun the
  documented `pnpm build` synchronization rather than hand-maintaining the
  generated site copy.

an existing external asset receiving a manual brand-text correction, so the
