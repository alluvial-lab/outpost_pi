# Re-review: story-app-debug-log-adapter v2

## 1. Verdict

**NEEDS FIXES.** The prior blocker and most prior implementation defects were genuinely fixed: the adapter now writes capped snapshots, `export()` reads the file after a forced flush, loading and flushes are future-coordinated, `log()` catches `_debugEnabled()` failures, byte accounting is UTF-8, and the privacy registry tests are materially stronger. I would still not advance the story because the revised snapshot-write model introduced/left a clear-vs-flush race: `clear()` can wipe the file while an already-started snapshot write is still in flight, and that stale write can complete after `clear()` and resurrect cleared debug logs. There is also a remaining durability-comment overclaim about critical events being “already on disk.”

## 3. New-bug check

### Blocker — `clear()` can race an in-flight snapshot flush and resurrect cleared logs

- **Where:** `app/lib/data/debug/debug_log_impl.dart:191-204`, `app/lib/data/debug/debug_log_impl.dart:250-258`.
- **What:** `clear()` clears `_ring`, awaits load, writes `''` to the file, then cancels only the timer (`app/lib/data/debug/debug_log_impl.dart:191-204`). It does not wait for or serialize against an already-started `_flushFuture`. If `_flushNow()` has already entered its chained closure, observed a non-empty `_ring`, built `snapshot`, and started `file.writeAsString(snapshot, flush: true)` (`app/lib/data/debug/debug_log_impl.dart:250-258`), a concurrent `clear()` can write the empty file while that stale snapshot write is still in progress. If the stale write completes last, old debug lines reappear after `clear()` returned.
- **Why it matters:** The story acceptance criterion says `clear()` wipes ring + file. Because debug logs intentionally contain operator diagnostics and message previews, a best-effort clear is not enough; clear must converge to “no captured data on disk.”
- **Fix:** Put `clear()` on the same serialization path as flushes. For example, cancel the timer, await the current `_flushFuture` (or chain a clear operation after it), then clear `_ring` and write the empty file; alternatively add a generation token so any in-flight snapshot captured before clear is discarded before writing.

### Important — durability docs still overstate critical-event persistence

- **Where:** `app/lib/data/debug/debug_log_impl.dart:25-29`, `app/lib/data/debug/debug_log_impl.dart:148-151`, `app/lib/data/debug/debug_log_impl.dart:216-221`.
- **What:** The comments correctly say final dispose flush is fire-and-forget/best-effort, but the class comment still says critical events flushed immediately on `log()` “are already on disk” (`app/lib/data/debug/debug_log_impl.dart:27-28`). In reality `log()` schedules an unawaited `_flushNow()` (`app/lib/data/debug/debug_log_impl.dart:148-151`); a crash or process kill can still occur before the async write finishes.
- **Fix:** Reword to “critical events start a flush immediately and usually survive normal teardown; crash/process-kill durability is best-effort until a caller awaits a flush.”

### Reviewed non-issues / acceptable behaviors

- **Flush-chain reset race:** No issue found. The code has no `await` between reading `_flushFuture` and assigning the chained `thisFlush` (`app/lib/data/debug/debug_log_impl.dart:250-263`). If a later flush chains after `thisFlush` completes but before the earlier waiter clears, `identical(_flushFuture, thisFlush)` prevents the earlier waiter from nulling the later chain (`app/lib/data/debug/debug_log_impl.dart:265-269`).
- **`_ensureLoaded().catchError` swallowing errors:** Acceptable for this contract. The catch handler logs and clears `_loadFuture` for retry (`app/lib/data/debug/debug_log_impl.dart:109-112`), and public methods are specified to never throw. Callers see success/null rather than an exception, then later calls can retry.
- **`export()` on first use/no file:** Acceptable. After forced flush, `export()` returns `null` if `_filePath` is absent or the file does not exist (`app/lib/data/debug/debug_log_impl.dart:163-169`); this matches the empty-export test (`app/test/data/debug/debug_log_impl_test.dart:48`).
- **`export()` and corrupt/partial lines:** Mostly acceptable. `export()` reads line-by-line and skips lines that fail `jsonDecode` (`app/lib/data/debug/debug_log_impl.dart:172-180`), so a truncated final JSON line is dropped rather than returned. A decoder-level error is caught by the outer public catch (`app/lib/data/debug/debug_log_impl.dart:184-186`).

## 5. Action items

1. **Blocker:** Serialize `clear()` with `_flushFuture` so no stale snapshot write can complete after the clear. Add a regression test that starts an immediate flush and calls `clear()` while/just after the flush is in flight, then proves the file remains empty after the flush chain drains.
2. **Important:** Remove the remaining “already on disk” wording for critical events and document the real guarantee: immediate flush is started synchronously, but persistence is best-effort unless a lifecycle path awaits a flush.
3. **Nit/follow-up:** Remove the stale local `forbiddenKeys` duplicate in `app/test/domain/contracts/debug_log_test.dart:72-82` and use `kForbiddenKeys` directly in the no-forbidden-key test, so the expanded forbidden set has one source of truth.
4. **Nit/follow-up:** Fix the comment in `app/lib/domain/contracts/debug_log.dart:34`/`:42` that references `DebugLogImpl.kMaxFieldValueChars`; the actual constant is the domain-level `kMaxFieldValueChars` (`app/lib/domain/contracts/debug_log.dart:330`).
